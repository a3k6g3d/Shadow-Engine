# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Shadow is a Windows-only inference engine (Rust host + CUDA kernels it compiles itself) for one model family: Qwen3.8-Flash-Next mixture-of-experts GGUFs (48 layers, 512 experts, top 10). It is not a general LLM runner and it is its own engine, not a Strata copy (borrowed parts are credited in `NOTICE`). It ships as `shadow.exe` (CLI + OpenAI-compatible HTTP server with a chat/dashboard web page) and `shadow-ui.exe` (Tauri launcher).

**Read `docs/STATUS.md` before changing anything**: it is the append-only, numbered evidence log (every experiment, including the failures and the wrong turns), and its top paragraph is the current state. Other docs: `docs/USAGE.md` (every flag and environment variable), `docs/ARCH.md` (the model as math), `docs/SHADOW_PLAN.md`, `docs/BENCHMARKING.md`, `docs/TOOLS.md` (every tool under `tools/`).

## Build, test, run

- Build: `cargo build --release` is the whole build. No nvcc/CMake needed: kernels in `kernels/*.cu` are compiled at run time by NVRTC (cache in `%LOCALAPPDATA%\Shadow\kernels`) and launched through the hand-bound driver API (`nvcuda.dll`).
- **Windows locks a running exe.** The user's launcher runs `target\release\shadow.exe`; for experiments and tests build into a separate dir: `CARGO_TARGET_DIR=target-dev cargo build --release -p shadow`. Check no `shadow.exe` / `shadow-ui.exe` is running before rebuilding `target\release`.
- Tests: `cargo test --release -p shadow-cuda --lib`, `-p shadow-serve --lib`, `-p shadow-model`. One test: `cargo test --release -p shadow-serve --lib semsearch::tests::the_right_file_is_found_by_the_words_of_the_question`. Tests that need the embedder or a model are `#[ignore]` (run with `-- --ignored`). GPU tests (`crates/shadow-cuda/tests/*.rs`, `--test pinned`) skip themselves with no CUDA device. `crates/shadow/tests/*.rs` read the model path from `SHADOW_MODEL`. There is no CI or clippy config in the repo.
- Optional native DLLs (nvcc + MSVC; run `.bat` files through `cmd /c`): `native/mmq/build.bat` (llama.cpp's int8 MMQ for dense projections) and `native/fused/build.bat` (Strata's fused int8 MoE kernels). The DLLs are git-ignored and loaded at run time (`Dylib`); a checkout without them runs the engine's own kernels. Both default to the ggml headers in `J:/Strata-work/...` (`GGML_DIR` overrides).
- Run: `shadow serve MODEL.gguf [--exact] [--port N] [--ram-tier-gib N|auto] [--ram-floor-gib N]` (default port 8081 is the user's own server; chat UI at `/`, Dashboard `#dash`, `/health`, `/v1/telemetry`, `/v1/tools/execute`). The model used for every measurement is the 2-shard Swift IQ3_S GGUF under `J:/Strata-work/models/swift15/IQ3_S/` (pass the `-00001-of-00002` file).
- **Never load a model outside `tools/run_capped.ps1`** (`-CapGiB N -FloorGiB 3 -Out log -Exe ... -Arguments '...'`): it caps the working set and kills the process below the free-RAM floor. Test servers use their own ports (8091 / 8095), never 8081; stop them by port only, never kill the user's `shadow.exe`.

## Architecture (the parts that span files)

- **`shadow-model`**: GGUF parsing, dequantization, tokenizer, and the scalar **CPU reference forward pass** (`forward.rs`) that every GPU path is checked against. `Model::load` keeps every dense tensor in RAM (CPU path, tests); `Model::load_lean` (the server) reads big dense weights from the file only while uploading them.
- **`shadow-cuda`**: driver API (`driver.rs`), NVRTC (`nvrtc.rs`), the kernel registry (`kernels.rs`: every entry point and its argument types must be registered there to be launchable from `kernels/*.cu`), and `GpuSession` (`session.rs`, very large): dense weights on the GPU, the expert caches, the decode path (CUDA graphs, speculative drafters in `session_mtp.rs` / `session_dflash.rs`) and the prompt path (2,048-row sub-chunks, a per-layer expert **stage pipeline** in `session_pipeline.rs`, a device-side MoE planner, a "lend" of the VRAM expert cache to the prompt).
- **Memory tiers for the routed experts**: VRAM cache (VRAM is full by design) -> pinned RAM tier -> NVMe (`ReadPool`). The RAM tier (`pinned.rs`) is a reserved address range committed and `cuMemHostRegister`ed in 1 GiB chunks: experts never cross a chunk boundary, each chunk has its own device address (`dev_addr`), and a watchdog gives chunks back when available RAM falls under `--ram-floor-gib` (acted on only between steps/batches). The `shadow serve` default tier (set in `crates/shadow/src/main.rs`) is sized from free RAM at start (`tier_for_available`, up to 45 GiB). An expert is one contiguous `[gate | up | down]` blob in a cache slot, ring slot or stage half; kernels and the planner address experts through per-layer device tables (`dp_eaddr`).
- **RAM floor is advisory in the tree as of v0.1.34 (uncommitted work by another agent, STATUS 94):** `PinnedRegion::new` / `new_chunked` only log `RAM warning:` when pinning would leave less than the floor free; the watchdog trims chunks afterwards. `with_ram_source` stays strict. `crates/shadow-cuda/tests/pinned.rs::refuses_the_real_machine_too` still expects a refusal from `new` and would now pin almost all free RAM: do not run `--test pinned` until that test uses `with_ram_source`.
- **Two modes**: `--exact` is bit-for-bit the reference; the default fast mode is deliberately inexact (tensor-core prompt kernels, int8 MMQ and fused int8 MoE via the native DLLs, speculation, tail skipping). A new fast path must be off under `--exact`, have an off switch (`SHADOW_X=0`), and be gated on fidelity (`tools/needle_test.py`, `tools/long_agree.py`, `tools/quality_test.py`). Note the short suites (`quality_test`, `task_check`) never reach the long-prompt MoE path.
- **`shadow-serve`**: hyper HTTP server; `engine.rs` is a single thread that owns the `GpuSession` and takes requests over a channel (prefix cache, conversation snapshots, picture encoding). `ui.rs` is one embedded HTML/JS page (chat, Dashboard, Settings; its poll of `/v1/telemetry` drives the status pill). `orchestrator.rs` runs the agent tool loop (read/edit/grep/cmd/web tools, recall, notes, `search`); `semsearch.rs` is the `search` tool (BM25 + a `llama-embedding.exe` subprocess; embedded text must stay under 510 tokens or the embedder aborts).
- **`shadow` (CLI)**: `crates/shadow/src/main.rs` applies the default serve flags (tier sizing, floor, drafters) before calling `shadow-serve`. `shadow-ui` launches/stops that server. `shadow-bench` and `shadow-eval` are the benchmark runner and the memory-retrieval yardstick.

## Working conventions

- **Every experiment gets a dated, numbered entry appended to `docs/STATUS.md`** with the measured numbers, what was not measured, and what is open; losses and wrong turns are recorded as plainly as wins.
- A change that ties or beats the default goes in as the default with an `=0` off switch; only measured losses stay opt-in.
- Measure with fresh servers and interleaved A-B-B-A pairs; wall-clock noise is about +-8%, so judge kernels by kernel time (nsys needs `--cuda-graph-trace=node`) and prompts by repeated pairs (`docs/BENCHMARKING.md`).
- The working tree is shared: the user's in-app chat agent edits `crates/shadow-serve` (notably `ui.rs`, `orchestrator.rs`, `engine.rs`) and leaves it uncommitted. Commit only your own hunks (extract them from `git diff -U0` and `git apply --cached --unidiff-zero`), never stash, reset or switch branches, and push only when asked.
- Python one-liners with backslashes or heredocs break under the Windows shells: write a script file in the session scratchpad instead.
