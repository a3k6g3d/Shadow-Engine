## 1. Goal

An .apk the user installs on their Android phone that connects to Shadow running on
this PC from across the room or away from home. The model, tools, memory and tier
stay on the PC; the phone is a thin client — like Claude Code Remote Control and
Antigravity Remote Control work.

## 2. What those two do (research, cited)

- **Claude Code Remote Control** ([code.claude.com/docs/en/remote-control](https://code.claude.com/docs/en/remote-control),
  [mobile](https://code.claude.com/docs/en/mobile)): the phone app is a client for
  sessions running elsewhere. You start it with `/remote-control` in a session, open a
  link or scan a QR from the app; files, MCP servers and tools stay on your machine.
  Push notification when a long task finishes. Their cloud brokers the connection —
  we have no cloud, so ours goes direct over LAN or Tailscale instead.
- **Antigravity Remote Control** ([antigravity.google/docs/remote-control](https://antigravity.google/docs/remote-control)):
  drive desktop sessions from any web browser over a secure channel. Their "Remote
  Agents" ([docs](https://antigravity.google/docs/remote-agents/)) run on Google's
  servers — not applicable to us; the thin-client + secure-channel model is.

Both patterns: **thin phone client + pairing + a secure channel.** Shadow already has
the first half of the pattern built (see §3); we need pairing, the channel policy, and
the .apk.

## 3. What Shadow has today (verified in this session)

- `shadow serve MODEL [--host H] [--port P]` — hyper + tokio, binds whatever `--host`
  says (`crates/shadowzero/src/main.rs:425–426`, default `127.0.0.1:8081`). `--host 0.0.0.0`
  works today, no code change.
- Routes in `crates/shadowzero-serve/src/lib.rs` (route table ~172–306): `GET/POST
  /v1/chat/completions`
  (OpenAI format, `stream: true` works — the embedded UI streams it with `fetch` +
  `getReader`, no EventSource/WebSocket), `/v1/tools` + `POST /v1/tools/execute`,
  `/v1/memory` CRUD, **`/v1/sessions` CRUD + `/v1/sessions/import` (server-side chat history,
  shipped 2026-11-16, `sessions.rs`)**, **`GET /v1/events` (SSE push hub, `events.rs`)**,
  `/v1/tree`, `/v1/file`, `/v1/telemetry`, `/v1/browser/screenshot`, `/health`, `/v1/status`,
  `/props`, `/metrics`, `POST /shutdown`, and `GET /` serves the embedded UI.
- The embedded UI is **browser-capable**: it talks to the server with relative `fetch`
  calls only, no Tauri IPC. It already has a viewport meta (`ui.rs:30`) and
  one mobile breakpoint (`ui.rs:963`, max-width 800px).
- **No auth, no CORS/OPTIONS handler anywhere** — the UI is same-origin, so it never
  needed them (verified: no `Authorization`, `Access-Control` or `OPTIONS` match in
  `shadowzero-serve`). Permission modes (Auto / Accept
  edits / Bypass) are enforced client-side; `POST /v1/tools/execute` runs whatever the
  client asks for. Conversations used to live in *that webview's* localStorage; they are
  on the server now (`/v1/sessions`, one JSON file per chat under
  `%LOCALAPPDATA%\ShadowZero\sessions`) and `ui.rs:3624–3630` migrates the old
  `shadow_chats_v1` store once and deletes it — so a phone connecting sees the desktop's
  history from the first build.
- Picture input works server-side (vision + image_pad handling, `lib.rs:21` `pub mod vision`,
  `IMAGE_MARK` `lib.rs:321`, `data:image/...;base64,` extraction `lib.rs:401–430`) —
  phone-camera photos in OpenAI message format are basically free.
- Toolchain on this box (re-verified 2026-11-17): JRE 17 only (Adoptium Temurin 17.0.21 —
  `java` runs, **`javac` is not on PATH**), **no Android SDK, no adb, no gradle, no
  sdkmanager/apkanalyzer**, `ANDROID_HOME` unset, `%LOCALAPPDATA%\Android\Sdk` absent.
  `winget v1.30.300` is available, and free space is ample (J: 71 GiB, C: 446 GiB), so the
  ~1.5 GB install is unblocked. Building an .apk here still needs a full JDK + SDK.

## 4. The plan

### Phase 0 — works today, zero code (kept as the Phase 1 test path)
Open Chrome on the phone to `http://<PC-LAN-IP>:8081` on the same Wi-Fi and
*Add to Home screen* (PWA-style icon, own storage). Prereqs:
1. serve bound to LAN: `--host 0.0.0.0` (or the same in the desktop's config),
2. Windows firewall: allow inbound TCP 8081 on *Private* networks only,
3. PC awake (SOPHOS sleep settings as usual).
Phone browsers allow cleartext HTTP today (it's only *native* apps that block it, API
28+), so this works with no server change. Caveats: no pairing/auth — see §5; history
is the phone's alone; no notifications.

**Tailscale variant of Phase 0 — DECIDED 2026-11-13, and the cheapest away-from-home win:**
install Tailscale on the phone *and* the PC (free, no server code), open Chrome to
`http://<PC-tailnet-IP-or-MagicDNS-name>:8081` — same served UI, works away from home,
and **no firewall rule at all**: Tailscale's own ACL/accepts gate the port, so the Private-
network inbound rule only matters for plain-LAN use. MagicDNS gives the PC a tailnet FQDN
(`machine.tailnet-name.ts.net`, short name resolves inside the tailnet —
[tailscale.com/docs/features/magicdns](https://tailscale.com/docs/features/magicdns),
[flaviocopes.com/courses/tailscale/use-magicdns-and-test-the-path/](https://flaviocopes.com/courses/tailscale/use-magicdns-and-test-the-path/))
so the address field can take a name instead of an IP, which survives reboots and IP leases.
Still no auth (the tailnet is the access control here). History is **not** the phone's alone
anymore: `/v1/sessions` is live server-side, so Chrome on the phone already shows the desktop's
chats (the one caveat: the phone's own browser storage is separate, so a phone-side chat is not
mirrored to the server until the Phase 2 app posts it). No notifications yet.

### Phase 1 — small additive server deltas — **SHIPPED 2026-11-17** (auth.rs + lib.rs + ui.rs; 66 tests green)
1. **Pairing + token** (Claude-style) — **DONE**: `crates/shadowzero-serve/src/auth.rs`
   (`Pairing`: 4-digit pin, 5-min TTL, 5 wrong tries, constant-time hash compares, token = 32
   random bytes hex, only its SHA-256 on disk at `%LOCALAPPDATA%\ShadowZero\pair.json`).
   `POST /pair` exchanges the typed pin for the client token (its only showing, ever); a
   middleware in `lib.rs` rejects non-loopback peers on `/v1*` without a valid
   `Authorization: Bearer` (or `?token=` fallback for SSE, since EventSource cannot set
   headers); loopback stays exempt so the desktop UI and benches never break. `/shutdown`
   and `/v1/tools/execute` are now covered by the same gate for LAN peers.
   **Desktop pin dialog**: the Settings view of the embedded UI (`ui.rs`, "Remote access"
   card) shows the pin with its expiry countdown (`GET /pair/pin`, loopback-only), the
   paired state (`GET /pair/status`), and forgets the device (`DELETE /pair` — an empty
   token is honoured for this machine only; a remote device must present its own token).
   **LAN bind**: already shipped as `shadowzero serve MODEL --host 0.0.0.0:8081`
   (`crates/shadowzero/src/main.rs:425`); the auth gate engages automatically for peers
   whose socket address is not loopback.
2. **CORS — DONE (shipped anyway)**: `auth::cors` runs on every reply in `lib.rs` — reflects the
   request's `Origin` with `Access-Control-Allow-Origin`, methods and headers (incl.
   `Authorization`), `Access-Control-Max-Age: 86400`, and answers `OPTIONS` preflight before the
   token gate. OkHttp is not CORS-bound, so the native app does not need it, but it costs one
   function and keeps the WebView-shell escape hatch and any browser client working.
3. **Server-side shared history — DECIDED 2026-11-13, SHIPPED 2026-11-16** (commit `434f8e2`, not
   under the name this plan proposed): the store both clients read is **`/v1/sessions`** — `GET`
   the sidebar rows, `POST` a whole conversation `{history, notes, id?}`, `GET /v1/sessions/<id>`
   the full history, `PUT` a rename, `DELETE`, `POST /v1/sessions/import` for a client's local
   store (`lib.rs:267–283`, `sessions_api` `lib.rs:900–948`, `sessions.rs`: one JSON file per chat
   under `%LOCALAPPDATA%\ShadowZero\sessions` + `index.json`, `KEEP_SESSIONS = 200`, ids validated
   `c` + alphanumerics ≤ 24 chars, all IO in `spawn_blocking`). The desktop UI already migrated off
   localStorage (`ui.rs:3624–3630`). So the app talks to `/v1/sessions` from its first build and the
   phone sees the desktop's history immediately; on-device Room/DataStore stays as the offline
   cache, and the swap to the server as the source of truth is only the DAO.
   **Two deltas the shipped store still needs for the phone**: (i) there is **no per-message
   append** — `save` rewrites the whole conversation, so a 662-message chat (the biggest row live
   today) is re-POSTed on every turn from a phone on Wi-Fi; an `append` route (or a client-side
   debounce) is worth adding before the app streams long chats; (ii) it is **unauthenticated like
   everything else** — once Phase 1's token middleware lands, `/v1/sessions` must be token-checked
   for non-loopback peers (loopback stays exempt), because it holds the user's transcripts.

### Phase 2 — the .apk (the deliverable): native Kotlin/Compose client (decided 2026-11-13)
~1 week, including the one-time toolchain install (§7 tail). Kotlin + Jetpack Compose; minSdk 24 —
the AndroidX default now ([developer.android.com/jetpack/androidx/versions](https://developer.android.com/jetpack/androidx/versions),
[issuetracker.google.com/issues/474169350](https://issuetracker.google.com/issues/474169350)) —
compileSdk 37 / min AGP 9.1.1 on the Aug '26 BOM ([android-developers.googleblog.com/2026/08/jetpack-compose-august-2026-release.html](https://android-developers.googleblog.com/2026/08/jetpack-compose-august-2026-release.html))
or pin an older BOM to stay on AGP 8.x.

- OkHttp streaming SSE straight to `/v1/chat/completions`; the app replicates in Kotlin the agent
  loop the desktop UI runs in JS today (`GET /v1/tools` fetch at `ui.rs:2015`, `POST /v1/tools/execute`
  at `ui.rs:2471`): tool cards + approval buttons (Auto / Accept / Bypass — same client-side rule §5).
- Memory browser via `/v1/memory`, `/v1/status` health dot, camera/share-sheet photo → base64 image
  message (server-side vision already works: `pub mod vision` `lib.rs:21`, `IMAGE_MARK` `lib.rs:321`,
  `data:image/...;base64,` extraction `lib.rs:401–430`).
- Conversation persisted on-device (Room/DataStore) as the offline cache, AND mirrored to the
  **server-side store `/v1/sessions`, which is already live** (Phase 1 item 3, shipped 2026-11-16):
  the phone reads the desktop's chats from its first build instead of waiting for Phase 3. One
  storage layer, so the swap of source-of-truth is only the DAO; mind the whole-conversation
  `POST` (no per-message append yet — debounce it on the client until that route exists).
- Server address is a field on the pairing screen (LAN IP or tailnet name) — decision 2:
  Tailscale gets you there with no server code; the app just needs to point at it.
- `network_security_config.xml` cleartext exception (Android blocks cleartext for apps, API 28+ —
  [developer.android.com](https://developer.android.com/privacy-and-security/security-config));
  OkHttp is not CORS-bound, so the CORS handler stays with the fallback only.
- Notifications: foreground service keeps the SSE stream open, local notification when a long turn
  finishes — the §6(a) recommendation, now on the critical path.
- Engine politeness: the server answers one request at a time (`lib.rs:3`) — phone and desktop
  contend on that one queue; the app keeps exactly one in-flight request, no session ownership.

**Fallback (demeasured, was the recommendation): WebView shell** — ~200-line Kotlin app hosting the
existing served UI at `http://IP:8081/`, plus pairing screen and the CORS handler (a WebView *is*
CORS-bound), plus the mobile CSS pass on ui.rs (the one breakpoint, `@media (max-width: 800px)`
at `ui.rs:963`). If native slips, this is
the 2-day escape hatch; the toolchain install serves either path.

## 5. Security

- Binding `0.0.0.0` without a token = anyone on the LAN can run tools and `POST /shutdown`.
  **Shipped 2026-11-17**: the Phase 1 pairing token gate covers every `/v1*` route (tools,
  sessions, chat, telemetry, `/shutdown`) for non-loopback peers; loopback stays exempt
  (no change for desktop/bench). `/pair/pin` answers on loopback only, so a LAN peer can
  never fetch the pin behind your back.
- Cleartext HTTP on Wi-Fi means the token is sniffable by anyone on the network. For
  *away-from-home*, **Tailscale — DECIDED 2026-11-13** (free, zero server code — connect to the
  tailnet IP) rather than building a relay; that is our stand-in for the "secure channel"
  both Claude and Antigravity lean on. On the LAN, the network_security_config pins
  cleartext to the subnet. Over Tailscale the cleartext exception is moot (the tunnel is the
  transport) — keep the app's address field able to take `http://<tailnet-name-or-IP>:8081`.
- The approval model (Auto/Accept/Bypass) is client-side; a malicious client could
  bypass it. Acceptable for a single-user LAN; note it in the plan's threat list.

## 6. Notifications (the Claude-app killer feature)

No cloud → no FCM without Google. Options: (a) **now on the critical path** (native decided) — a
foreground service that keeps the SSE stream open and fires a local notification when a long task
finishes (works while the app is alive or resurrected by the service); (b) WebView-shell fallback —
best-effort `WebNotification` while the page is open; (c) later, a `POST /v1/push` hook the server
calls on `finish` that the phone polls cheaply. Ship (a) in the first .apk; (c) is the cheap way to
catch the "app was killed" case, worth doing early.
**(a)'s transport is already built**: subscribe to `GET /v1/events` (`events.rs` `EventHub`,
`lib.rs:303` / `sse_events` `lib.rs:988+`) — it already pushes telemetry ticks, engine-status
changes and tool results, so no new server code is needed for the notification itself; the app
only needs to detect the turn boundary (the `finish` tool result, §4 Phase 2) and post a local
notification. Two constraints from the shipped hub: it is a `broadcast` with `CAPACITY = 256` that
**drops** events for a slow subscriber and has **no replay**, so after any reconnect the app must
resynchronise from `/v1/sessions` + `/v1/telemetry` rather than trusting missed events; and a
browser tab and the phone share the same hub, so per-client filtering is the app's job.
